# Start from the one architecture

Answer a direct question first, at the requested length; a question alone does not commission implementation.
Then, for any substantive work:

1. **Recover the request from the Founder's own words.**
  Read the whole current conversation as one requirement; a correction adds constraints unless the Founder says stop.
  When continuity matters, use `mine-transcripts`; an agent summary or an agent-written record is never the source.
  A repeated ask raises priority; it never requires the Founder to explain the engineering again.
2. **State the change inside the architecture before making it.**
  Name the object types (registry, or `specializeType` over an upstream type), the morphism (registry, `jsnode_search`, `jsnode_typeflow_type`, `jsnode_functions`), the engine it composes through, the effect owner it reaches the world through, and the record it leaves.
  If any of those is missing upstream, seating it upstream is the first lot of the work, never a local stand-in.
  If a capability already has two implementations, the registry's owner stays, the other is deleted, and its consumers migrate in the same change; a surviving look-alike is a question for the Founder.
3. **Work from the primitives outward.**
  A leaf is touched only after its upstream owner is right.
  Never begin at the leaf because it is the first change found.
4. **Load only the skills the work and its checks need.**
  Discovery: `census-existing-code`, `search-knowledge`.
  Change: `migrate-consumer`, `seat-reusable-jsnode-package`, `consume-jsnode-package`.
  Release: `publish-package`, `release-jsnode-npm-package`.
  Close: `use-git`, `close-session`.
  Harness: `maintain-claude-harness`, `maintain-codex-harness`.
  Correction: `take-the-founder-seriously`.
  Program context: `align-to-roadmap` only when organizational context changes the outcome; a work-rail entry never gates the Founder's request.
5. **Finish through the operators.**
  Publish and repin through `publish-package.mjs`; commit exact paths through `commit-git-paths.mjs`; verification is a command's exit status.
  Report what was checked, what was not, and what remains.

## Systemic replacement

When the Founder names an end-to-end system, a family of consumers, or a drift from shared upstream capability, the request is a systemic replacement: recover the live topology (owners, consumers, effect boundaries), name the canonical transformation and the competing paths to delete, state the cutover order with the real receiver at each stage, then run implementation lots that each have a declared shared owner, a real consumer migration, and a superseded mechanism to remove.
A package-local green test is evidence for that lot, never that the system was repaired.

## Repair a demonstrated skill defect

Change a skill only for an explicit request or a concrete procedural defect this session exposed.
Edit the authored source under the projection service's `content/skills/`, reproject through `maintain-claude-harness` and `maintain-codex-harness`, reload the changed skill, and distinguish a text check from observed behavior.
Replace defective guidance; never accumulate incident prose.
Delegated agents inherit the relevant skills and report friction; they do not commission another improver.
