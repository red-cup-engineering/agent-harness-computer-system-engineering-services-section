# Maintain the harness from authored sources

Repair the requested harness capability. Application examples identify the
behavior to prevent or enable; they do not authorize application work.

## Find and repair the source

Follow a generated header or configured source to the authored harness policy,
skill, machine projector, or generic projection service. For systemic repeated
behavior, repair the shared decision rule. If an applicable rule identifies a
concrete architectural violation and replacement, repair the shared owner
directly. An evident stale projection can follow its source directly.

Do not hand-edit `AGENTS.md`, `.codex/config.toml`, `.agents/skills`, or
`.codex/agents`. Keep actor identity, office constitution, incumbency, duties,
provider role, and projected configuration distinct when those are involved;
a runtime description does not become their canonical source.

Change the authored owner, inspect its diff, run its projection, and check the
resulting runtime files. Verify the actual installed dependency used by the
projector; editing a repository source does not update an installed package.
Preserve unrelated configuration and the requested scope.

Use [improve-skills-before-work](../improve-skills-before-work/SKILL.md) for an
explicit skill repair or demonstrated procedural defect. Normal turns only
load their governing skills. Lifecycle facilities may record real work for an
operating consumer; they must not impose automatic mutation, receipts, or
ceremonial permission gates.

## Share the implementation

When both harnesses need the behavior, use one generalized office, duty, agent,
skill, character, or other lawful upstream owner and make each harness a
generated consumer. Codex must not require Claude's runtime directory or
implementation merely because both project the same capability. Do not pursue
parity unrelated to the request.
Runtime configuration, supported tools, identity, and credentials may differ.
Verify affected consumers of the shared behavior.

## Verify what changed

Run focused owning tests and inspect authored and generated diffs. Check
projection currency and repeatability where applicable, then exercise the
requested startup, MCP, agent, or skill behavior when practical. A renderer
or frontmatter check proves propagation or structure, not engineering judgment.
For a procedural change, use realistic forward cases with their raw artifacts
and inspect the acting agent's choices and outcomes; do not pass it the expected
answer. Report unexercised behavior or a fresh-session activation gate plainly.

Completion requires the authored source, current projection, applicable checks,
and observed requested behavior or an explicit remaining activation gate.
Keep the committed cut to intended authored and generated paths. Do not add a
generic verification wrapper or incident recipe merely to claim evidence.

## Forward cases

- Stale generated wording is repaired at its source and projected; unrelated
  settings survive.
- An installed package still renders old instructions despite updated source:
  correct the consuming installation and reproject before claiming activation.
- A missing MCP registration is repaired at its owner and observed in a fresh
  runtime, or fresh-runtime verification is reported as pending.
- Correctly rendered instructions produce a leaf repair on a systemic case:
  treat that as a behavioral failure despite passing projection tests.
