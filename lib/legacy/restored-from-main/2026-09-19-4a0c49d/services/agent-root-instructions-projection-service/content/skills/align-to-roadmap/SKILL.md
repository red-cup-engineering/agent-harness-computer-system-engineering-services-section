# Align work to the requested outcome

Start from the complete current request. The user settles purpose, scope, and
acceptance; the agent supplies engineering judgment and carries authorized work
through to its receivers. A harness or instruction-only request changes only
those sources and projections, even when examples name applications. A later
restriction or stop controls earlier commissions and standing priorities.

Treat a correction as an added constraint unless it explicitly replaces the
request. Preserve the overarching purpose while identifying the immediate
authorized action. When actionable work must be durable for an operating
consumer, recover the original user source, use the existing structured intent
and discharge operations, link endeavor, project, plan, and executable tasks
where the existing model requires them, and read the resulting work back. Do
not turn an example into the whole scope or create a parallel demand log.
For work-intent admission, retain the subject returned by
`structured_work_intent_admit` and call `work_item({ input: { id: subject, date } })`.
Confirm the returned roadmap nodes or milestones carry the expected parents,
status, and readiness. The admission feed id selects a feed, not scope; an
admission receipt is not readback.

Preserve an already-settled
architecture across the requested domains; do not reopen it as a review gate,
substitute an app-local repair, or require the user to name the shared primitive.
An evident confined correction can proceed directly.

## Consult the existing roadmap

Read the derived roadmap readout through the work rail's `agent-work-dispatch`
at ops.561.group or `derive-roadmap-readout` in
roadmap-engineering-services-section, plus the authoritative carriers needed
for the current outcome. Reuse current verified context. If the route is absent
or refused, use available grounded source retrieval and state the unsupported
part; missing machinery does not veto authorized work.

The roadmap derives from journaled structured work and provenance. Do not read
or write a handwritten goal stack as its authority. The governing record is
`561-group-services-section/data/records/2026-09-06-ruling-roadmaps-are-derived-from-journaled-work-never-handwritten.json`.
Use existing intent and discharge operations when work-state recording is
needed by an operating consumer; do not create a competing roadmap or artifact
merely to begin work.

Identify the requested capability, observable usable outcome, and dependencies
or missing reactions that prevent it. Sequence against that evidence while
preserving the whole authorized scope. Rankings inform order; they do not
replace the user's outcome with the easiest local task.

## Preserve purpose and complete the work

For work within an existing long-horizon program, use its canonical subject
carrier and preserve the full named dimensions, receivers, and material
uncertainties. Update it in place only when purpose, shipped state, a material
uncertainty, or the current edge actually changes within the requested scope.
Do not create a carrier, plan, receipt, or organization record as an admission
gate for an ordinary repair. Program prose must not delay implementation;
explicit program formation follows its own requested scope.

Follow real dependencies, repair shared owners, connect the necessary consumers,
and observe the requested human, agent, deployed, or public receiver. The
architecture procedure determines how broadly to consolidate or replace the
system; the first visible path does not limit an authorized overhaul.

Use available providers when delegation is authorized and useful. Each lot
names actual dependencies, the capability it produces, its receiver, and
observable acceptance. Keep shared assumptions and whole-outcome integration
with the receiver. Distinguish actor, office, duty, skill, operation, and runtime
provider when those relations matter; missing institutional detail is relevant
only if it blocks the requested capability. Do not require an office transition,
mandatory delegation, or a fabricated organization chart before otherwise
authorized implementation.

Apply the provider and context-cost discipline in
[improve-skills-before-work](../improve-skills-before-work/SKILL.md).

Tests, installation, publication, deployment, credential induction, and live
receiver behavior are distinct gates. Report what actually changed and the
remaining requested gates; passing source tests do not establish a shipped or
usable result. Scientific investigation and collaborative architecture review
are valid outcomes when requested, without an implementation or earnings
substitution.

## Respect user effort and the requested economic outcome

Distinguish the user's hands, frontier sessions, commissioned lots, and
production machinery. Use existing deterministic machinery for mechanical work
and reserve inference for judgment. Spend user attention on decisions, identity,
and actions that require it. Compare total work and maintenance burden, not
just the size of a patch or one model call; label estimates and measurements
honestly.

For an earnings request, identify the intended receiving account or wallet and
the target for first cash. Connect enabling research, plans, or measurements to
the actual earning action in the same authorized work. Rank opportunities by
expected cash relative to user effort and machine cost; preserve credential,
account, capital, and signature authority. Report actual received amounts and
dates only from evidence. Catalog entries, capabilities, transactions awaiting
settlement, and revenue are distinct. An earnings rule does not redirect a
scientific or architecture request.

For work under the Group's existing attention-investment plan, consult its
carrier rather than restating its participation, capital, and first-customer
constraints:
`561-group-economic-operations-services-section/content/text/documents/articles/notes/2026/09/06/2026-09-06-note-on-investing-the-group-s-attention-across-its-economies.md`.
Use its attention allocation when applicable; do not create a new program
record merely to classify the session's cost.

## Forward cases

- An ordinary correction creates no program carrier and proceeds without an
  office transition or compulsory delegation.
- A broad cross-domain overhaul preserves its full consumer scope while work
  is sequenced; the first broken path is not a boundary on consolidation.
- An existing program's purpose survives a local work lot, with a carrier update
  only for a material change, not a session diary or duplicate roadmap.
- A harness example naming an application changes only instructions and their
  projections; a stop redirects affected delegated lots as well as local work.
- A control-plane request reports authentication, installation, and live
  receiver evidence separately.
- An earnings request reports measured receipts separately from projected cash;
  a requested research result is assessed as research rather than cash.
